# Agent Note: Prompts — named templates typed into a focused Agent

Status: implemented

## Problem

Agents are interactive REPLs: the only way to get context (current file, line,
function, class) into one is to type it. There was no way to recall a canned
message — every question had to be retyped by hand. sidekick.nvim solves this
with named prompt templates selected from a picker; Vantage wanted the same,
scoped to "select a prompt and type it into the focused Agent's input".

## Decision

`prompts` is a top-level `setup` table mapping names to string templates, with
two built-in identity defaults `{file}` → `{file}` and `{line}` → `{line}`
(see the [built-in-defaults note](2026-09-01-prompts-built-in-defaults.md));
`cli.tools` remains empty. `:Vantage prompt` opens
`vim.ui.select` to choose one (not the pluggable Picker — nothing to preview);
the chosen template is rendered and typed into the
focused Agent's pane via a new Backend method `send_keys(target, text)` — a
literal `tmux send-keys -l` plus a trailing LF, with no Enter, so the user
reviews before submitting. The focused Agent is `Client.last_agent_alive()`.

Four placeholders, all Claude-style location references relative to the focused
Agent's cwd: `{file}` (`@<relpath>`), `{line}` (`@<relpath> :L<row>`),
`{function}` / `{class}` (`function|class <name> @<relpath> :L<row>:C<col>`,
via nvim-treesitter-textobjects' `@function.outer` / `@class.outer`). Context
comes from the most-recently-visited non-terminal window (a `WinEnter` stamp).
A placeholder that resolves empty skips the send with a warning; unknown
placeholders are left literal at runtime and reported as errors by
`:checkhealth`. Multi-line templates are typed with literal newlines (never an
implicit Enter).

A per-tool `format` hook (`cli.tools.<name>.format`, `fun(text): string`) runs
after render and before send, so a tool can rewrite the Claude dialect; the
Agent now remembers its `cli.tools` key (`@agent-tool` window option →
`Agent.tool`) to look the hook up. This is the one place the location syntax is
tool-agnostic.

## Alternatives considered

### Why not unify `{function}` and `{class}` into `{symbol}`?

sidekick keeps them separate because they are different treesitter queries that
answer different questions (the enclosing method vs the enclosing class), even
though they render identically. A unified `{symbol}` would have to pick a rule
(innermost wins) and would lose the ability to disambiguate; matching sidekick
exactly cost nothing here.

### Why not a single global `format` hook?

A single `format(text, agent)` function would leave per-tool dispatch to the
user (a `switch` on `agent.cmd`). Hanging `format` on `cli.tools.<name>` and
persisting `@agent-tool` makes it automatic and matches sidekick's per-tool
model; the cost is one Agent field and one window option.

### Why not pass the Agent into `format`?

The hook's job is syntactic rewriting after the semantics are already flattened
into the location string; the Agent runs in the very cwd the string is relative
to, so no re-relativization is needed. A pure `fun(text): string` is the
smaller, more testable surface.

## Consequences

- `{a|b}` alternation, `{input}`, and `{selection}` are deliberately unsupported
  (not planned); static prompts are just templates with no placeholders. A
  built-in prompt library — originally unsupported here — now ships as the two
  identity defaults `{file}` and `{line}` (see the
  [built-in-defaults note](2026-09-01-prompts-built-in-defaults.md)).
- Location references are Claude-dialect (`@file :L10`); other tools are
  expected to translate via `format`.
- A future zellij driver can express `send_keys` via `zellij action write`, but
  that acts only on the focused pane (no pane id), so it would need an
  attached, focused client and would lose tmux's "send while hidden" property.

The Backend method it adds extends [the backend-driver-seam note](../architecture/2026-08-31-backend-driver-seam.md).
